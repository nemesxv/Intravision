# Intravision

Веб-приложение, моделирующее автомат по продаже напитков. Реализует публичный интерфейс покупателя и административный интерфейс с доступом по секретному ключу в URL.

Основные инженерные задачи проекта: сохранение согласованности денежных и товарных остатков, обработка конкурентных запросов, расчёт сдачи при ограниченном запасе монет и разделение ответственности между интерфейсом, HTTP API и бизнес-логикой.

## Развёрнутая версия

- Пользовательский интерфейс: [http://95.165.103.141:5081/](http://95.165.103.141:5081/)
- Административный интерфейс: [http://95.165.103.141:5081/admin?key=5sBdg210XtM-t3PEo-yiT1PSillVyHdvjvrvVhFhU8w](http://95.165.103.141:5081/admin?key=5sBdg210XtM-t3PEo-yiT1PSillVyHdvjvrvVhFhU8w)
- Ключ администратора: `5sBdg210XtM-t3PEo-yiT1PSillVyHdvjvrvVhFhU8w`

Ключ опубликован только для проверки тестового задания. В рабочем окружении административный ключ должен передаваться через защищённую конфигурацию и не включаться в документацию или репозиторий.

## Функциональность

- Покупатель вносит монеты номиналом 1, 2, 5 и 10 ₽ и видит текущий баланс. Заблокированные номиналы выделены и недоступны для внесения.
- Нажатие на карточку с изображением покупает напиток. Товар без остатка или дороже баланса недоступен; сервер повторно проверяет условия.
- После покупки уменьшается остаток напитка, обновляется запас монет и выдаётся точная сдача. Блокировка приёма не запрещает выдачу монеты на сдачу.
- Администратор управляет названием, ценой, количеством и необязательным изображением напитков, удаляет товары, изменяет запас и блокировку монет. Все настройки монет сохраняются одним действием.
- Выполнены оба необязательных требования: JSON-импорт напитков и несколько покупок до получения сдачи.

## Технологии и структура

.NET 10, ASP.NET Core Web API, Entity Framework Core 10, SQL Server Express LocalDB; React 19, Vite 8 и Lucide React. Схема БД управляется миграциями Code First.

React отвечает за отображение и взаимодействие, Vite — за разработку и сборку клиента. ASP.NET Core обслуживает API и готовые статические файлы. Для обычного запуска приложения отдельный сервер Vite не требуется.

```text
ClientApp/src/                 React-компоненты и стили
Intravision/Controllers/       HTTP API и выдача двух страниц
Intravision/Requests/          Входные модели и валидация запросов
Intravision/Services/          Прикладная логика и инфраструктурные адаптеры
Intravision/Services/Contracts/ Контракты сервисов
Intravision/Models/            Сущности, денежные ограничения, общие правила
Intravision/Data/              DbContext, конфигурации сущностей и миграции
Intravision/Filters/           Проверка административного ключа и CSRF
Intravision/wwwroot/app/       Готовая сборка React
tests/                        Проверки алгоритма, сервисов и HTTP API
samples/drinks.json           Пример импорта
```

### Разделение ответственности

Контроллеры преобразуют HTTP-запросы в команды сервисов и возвращают результаты. Правила покупки сосредоточены в `VendingService`, административные изменения — в `AdminService`, запросы каталога — в `CatalogQueries`.

`IChangeCalculator` отделяет алгоритм сдачи от покупки. `IDrinkImportReader` отделяет разбор формата от сценария импорта, а `IDrinkImageStore` — файловое хранение от работы с напитками. Зависимости подключаются через DI; тесты подменяют парсер и хранилище без изменения прикладного сценария.

`DrinkRules` проверяет общие ограничения и при ручном вводе, и при импорте. `CustomerWalletAccessor` связывает HTTP-cookie с кошельком, а `WalletState` отвечает за сериализацию его состояния. EF Core используется внутри сервисов для запросов, отслеживания изменений и транзакций.

## Данные и согласованность

- `Drinks`: идентификатор, название, необязательный путь изображения, цена, количество, RowVersion.
- `Coins`: номинал как ключ, количество, признак блокировки, RowVersion.
- `CustomerWallets`: идентификатор, внесённые монеты, режим покупки, последний чек, RowVersion.

Цена и номинал имеют тип `decimal(10,2)`, чтобы денежные вычисления были точными. Цена положительна, количества неотрицательны; БД ограничивает номиналы значениями 1/2/5/10. Конфигурации EF Core содержат ограничения, точность полей и начальные записи монет.

### Выполнение покупки

1. Сервер проверяет версию кошелька, наличие напитка, его версию и достаточность баланса.
2. Доступный запас для расчёта включает монеты автомата и внесённые монеты покупателя.
3. Рассчитывается точный состав сдачи с учётом количества каждого номинала.
4. Остаток напитка, монеты и кошелёк сохраняются одной транзакцией.

Если точную сдачу собрать нельзя, покупка отклоняется без изменения баланса и остатков. RowVersion обеспечивает оптимистическую конкуренцию: устаревший запрос не перезаписывает свежие данные. Конфликт возвращается клиенту, который получает актуальное состояние и предлагает повторить действие. Это предотвращает двойное списание при повторе запроса с той же версией.

Внесённые монеты хранятся отдельно от доступного запаса автомата. В режиме «Несколько напитков» оставшаяся сдача также резервируется в кошельке. Изменение запаса администратором не расходует зарезервированные средства покупателя.

### Расчёт сдачи

Жадный выбор крупнейшего номинала недостаточен при ограниченном запасе: для 6 ₽ набор 5 ₽ × 1 и 2 ₽ × 3 требует выбрать 2 + 2 + 2.

Алгоритм переводит значения в целые денежные единицы, нормализует их по НОД и выделяет группы равной стоимости. Динамическое программирование проверяет достижимость остатка с ограничением количества монет. Для фиксированного набора номиналов размер этой задачи не растёт пропорционально балансу. Результат — допустимый состав точной сдачи; минимальное количество монет не является критерием оптимизации.

### Изображения и импорт

Файлы PNG/JPEG/WebP размером до 2 МБ проверяются по сигнатуре и получают случайные имена. При замене старый файл удаляется после успешной записи БД. При ошибке сохранения выполняется очистка созданного файла.

Импорт сначала проверяет все записи и изображения, затем сохраняет файлы и добавляет напитки одним вызовом SaveChanges. При обрабатываемой ошибке созданные файлы удаляются. Файловая система не участвует в транзакции SQL Server: аварийное завершение процесса между операциями может оставить неиспользуемые файлы. Для нескольких экземпляров приложения потребуется общее хранилище изображений.

## HTTP API и защита доступа

Страницы: `/` — покупатель, `/admin?key=...` — администратор.

```text
GET  /api/vending              Каталог, монеты, баланс, версия, чек, CSRF-токен
POST /api/vending/insert       denomination, version
POST /api/vending/purchase     drinkId, drinkVersion, version
POST /api/vending/return       version
POST /api/vending/mode         keepChange, version

GET  /api/admin                Каталог, монеты, CSRF-токен
POST /api/admin/drinks/save    Drink.Id, Name, Price, Quantity, RowVersion, Image
POST /api/admin/drinks/delete  id, rowVersion
POST /api/admin/coins/save     Coins[i].Denomination, Quantity, IsBlocked, RowVersion
POST /api/admin/drinks/import  importFile
```

В форме сохранения напитка все поля имеют префикс `Drink.`, а поля монет — `Coins[i].`. POST-запросы передаются как URL-encoded формы либо multipart/form-data для загрузок; ответы API — JSON. Клиент передаёт CSRF-токен в заголовке `X-CSRF-TOKEN`. Версии записей передаются в Base64.

Параметр `key` обязателен для административной страницы и каждого административного API. Ключ сравнивается через хеширование и сравнение фиксированного времени. Ответы запрещают кеширование; политика no-referrer ограничивает передачу URL при переходах.

Ошибки входных данных и CSRF возвращают 400, неверный административный ключ — 403, отсутствие удаляемого или редактируемого напитка — 404. Конфликт версий и отказ в операции покупки возвращают 409.

Кошелёк связан с cookie, защищённой ASP.NET Core Data Protection: HttpOnly, SameSite=Strict, Secure при HTTPS. Удаление cookie лишает браузер доступа к прежнему кошельку. Для переноса или нескольких экземпляров приложения необходимо сохранять и совместно использовать ключи Data Protection.

Доступ по URL-ключу реализует условие задания; это единый секрет без персональных учётных записей и ролей. При внешнем размещении следует учитывать наличие ключа в истории браузера и журналах запросов.

## Локальный запуск

Требуются Windows, .NET 10 SDK и SQL Server Express LocalDB. Команды выполняются из корня репозитория:

```powershell
dotnet restore Intravision.slnx
dotnet tool install --global dotnet-ef --version 10.0.11
dotnet ef database update --project Intravision
dotnet run --project Intravision --launch-profile http
```

Установка инструмента не требуется, если совместимый dotnet-ef 10.x уже доступен.

- Покупатель: http://localhost:5205/
- Администратор: http://localhost:5205/admin?key=intravision
- HTTPS: профиль `https`, адрес https://localhost:7009/. Для доверия сертификату: `dotnet dev-certs https --trust`.

`ConnectionStrings:DefaultConnection` в `Intravision/appsettings.json` указывает на `(localdb)\MSSQLLocalDB`, базу `Intravision` и Windows Authentication. Строка может быть переопределена через User Secrets или `ConnectionStrings__DefaultConnection`. Миграции применяются явно командой выше.

Ключ `intravision` задан в `appsettings.Development.json` исключительно для удобства проверяющего. В production этот демонстрационный ключ не должен присутствовать или использоваться. Задайте собственный `Admin__SecretKey` через окружение или хранилище секретов. Без настроенного ключа административный доступ закрыт.

При проблемах обнаружения существующей LocalDB-базы доступен `scripts/Connect-LocalDb.ps1`. Он проверяет подключение и обновляет User Secrets проекта. Если используется адрес именованного канала, повторная настройка может потребоваться после перезапуска LocalDB. Скрипт не создаёт и не удаляет базы.

### Начальные данные и импорт

Миграции создают четыре номинала с нулевым запасом и разрешённым приёмом. Каталог напитков пуст. В разделе «Импорт каталога» можно загрузить `samples/drinks.json`: вода за 20 ₽ и чай за 30 ₽. Пример содержит изображения-заглушки 1×1, которые можно заменить через редактор.

Формат импорта — массив объектов с обязательными полями `name`, `price`, `quantity`, `imageBase64`. Цена — JSON-число с точностью до двух знаков; изображение — Base64 без префикса data:image. Допускаются 1–50 записей и файл до 20 МБ; неизвестные и отсутствующие обязательные поля отклоняются. Импорт добавляет записи, повторная загрузка создаёт копии.

Для проверки сдачи задайте запас монет в административной части и нажмите «Сохранить монеты». Внесите 25 ₽ и купите воду за 20 ₽: остаток уменьшится на единицу, чек покажет 5 ₽ сдачи. Режим «Несколько напитков» сохраняет остаток для следующих покупок до явного возврата.

## Сборка клиента и публикация

Готовые файлы React находятся в `Intravision/wwwroot/app`. Обычный запуск .NET использует их без Node.js. После изменения React/CSS клиент необходимо пересобрать.

Требуются Node.js 22.12+ и pnpm 11.19.0:

```powershell
cd ClientApp
pnpm install --frozen-lockfile
pnpm run build
cd ..
dotnet publish Intravision -c Release
```

Для разработки запустите .NET с профилем http, затем `pnpm dev` из ClientApp. Vite использует http://localhost:5173/ и проксирует API на порт 5205.

## Проверки

```powershell
dotnet build Intravision.slnx -c Release
dotnet run -c Release --project tests/ChangeCalculatorChecks
dotnet run -c Release --project tests/ServiceBoundaryChecks
python tests/client_smoke.py
```

- ChangeCalculatorChecks: 115 251 сравнение с полным перебором, дробные номиналы, большие суммы и недоступная сдача.
- ServiceBoundaryChecks: подмена парсера и хранилища, валидация до побочных эффектов, очистка файлов при ошибках хранилища и записи БД.
- client_smoke.py: HTTP/SQL-проверки покупки, возврата, изоляции кошельков, блокировки монет, импорта, CRUD, изображений, CSRF и административного доступа. Включены конкурирующие покупатели и повторная покупка с одной версией кошелька.

HTTP-проверки требуют Python 3, dotnet-ef и sqlcmd. Они запускают приложение на порту 5192, создают отдельную LocalDB-базу и временное хранилище изображений, затем удаляют их. Проверки сервисов и алгоритма не требуют SQL Server. Другой адрес SQL Server можно передать через `INTRAVISION_TEST_SERVER`.

## Границы реализации

Проект моделирует один автомат. Реальные платежи, интеграция с оборудованием и персональные учётные записи не входят в область задания. Цены поддерживают копейки, но текущий набор целых номиналов не позволяет оплачивать дробную стоимость: если точной сдачи нет, операция отклоняется с сохранением баланса.

Клиент ограничивает время запроса и блокирует повторное нажатие во время операции. После ответа или ошибки он перечитывает состояние; покупка автоматически не повторяется. Это учитывает ситуацию, когда сервер завершил операцию, но клиент не получил ответ.
